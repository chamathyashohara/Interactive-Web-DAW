Stage 7 evidence: one-way live audio (producer -> performer), development PC, 11 Oct 2026
============================================================================================
PC: Windows 11 Pro 10.0.26300, Realtek audio (microphone endpoint MUTED in Windows -> digital
silence; speakers live, so the real-output run used -60 dB). Build: core-check-gcc (MinGW g++ 16.2,
NOT the MSVC product build). Commit: Stage 7 working tree on top of 12bf368.
All runs: TWO PROCESSES ON ONE PC. They test logic, codec, counters and robustness; they do NOT show
audio heard at a remote PC, real network behaviour, or acoustic latency.
"TEST TONE" = synthetic 440 Hz at -20 dBFS pushed every 10 ms into the live tap (not a microphone).
"TEST PLAYBACK CLOCK" = render_add() every 10 ms on a thread, output optionally saved to WAV (not a device).
Pairing codes are replaced by <redacted>.

Consequence: the sender uses select(1 ms) under timeBeginPeriod(1); the probe test clocks wait in

24 ms max gap caused by the test clocks; it is superseded by L1 below (scratch L1, not kept).

3. Two-process runs
----------------------------------------
Note: each LIVE SUMMARY is printed just BEFORE the sender/receiver stop, so the producer summary can
show slightly fewer packets than the performer received. The final counts are in the live log events.
COUNTER FIX found by these runs: in L1-L5 the sender packets_sent also counted the 2 END_OF_STREAM
datagrams, so the final sender_stopped count is exactly 2 above the receiver count in every run without test impairment.
packets_sent now counts AUDIO datagrams only (END_OF_STREAM has its own counter). L1-recheck is the
same run after the fix: 1202 sent, 1202 received.

4. Observations (measured here; one PC, loopback or own Wi-Fi address, test clocks unless stated)
----------------------------------------
- Live path works end to end (L1, L3):
  - every packet sent was received; 0 lost, late, concealed or invalid; 0 decode errors;
  - the sink is 440 Hz at -35.0 dBFS RMS. That is expected: the -20 dBFS-peak sine is -23 dBFS RMS, and the gain is -12 dB;
  - 0 dropout blocks and 0 dip blocks;
  - inter-arrival jitter 0.7-1.1 ms, largest arrival gap 13.4-13.7 ms (test clocks, one PC).
- Forced impairment (L2) did not crash either process. All of it was counted on both sides:
  - 299 packets dropped by the simulator; the receiver estimated 275 lost. The difference is the final 24-packet burst, which came after the last received packet and so cannot be inferred from sequence numbers;
  - 27 duplicates and 28 reordered packets detected;
  - 160 underruns, 8 refills (the stall limit is 20 frames, and each 250 ms burst exceeded it), 232 frames concealed;
  - playback resumed after every burst; 0 decode errors.
- Real devices (L4):
  - the WASAPI output callback ran at 48 kHz (0 wrong-rate callbacks);
  - worst render_add (queue + jitter buffer + Opus decode + mix) was 0.166 ms per callback;
  - 0 lost and 0 underruns; output peak -200 dBFS, i.e. silent: the microphone is muted, so this run shows the path, not audible content;
  - both master takes were complete (253 327 and 253 329 frames) in separate files while the live stream ran.
- Encode cost: the worst single Opus encode was 0.23-0.48 ms across the runs.
  - Lookahead read from libopus: 120 samples (2.5 ms) for RESTRICTED_LOWDELAY, 312 samples (6.5 ms) for AUDIO.
  - Packet size at 64 kbit/s CBR, 10 ms: 106 bytes per datagram (80 bytes Opus + 26 bytes header).
- Responsiveness versus stability (L5, one PC, test clocks):

  | Frame | Jitter target | Underruns | Concealed | Dropout blocks |
  |---|---|---|---|---|
  | 10 ms | 1 frame (10 ms) | 0 | 0 | 0 |
  | 10 ms | 2 frames (20 ms) | 0 | 0 | 0 |
  | 20 ms | 2 frames (40 ms) | 0 | 0 | 0 |
  | 2.5 ms | 4 frames (10 ms) | 635 in about 10 s (also 635 late) | 635 | 14 dropout, 38 dip blocks |
  | 2.5 ms | 8 frames (20 ms) | 0 | 0 | 0 |

  - Cause: the source and the playout run in 10 ms blocks, so 2.5 ms packets arrive four at a time and are pulled four per callback.
  - A 10 ms buffer leaves no margin. A smaller frame does not lower the usable buffer below the block period.
- NOT shown by these runs:
  - audio heard at a remote PC;
  - behaviour on a real LAN between two PCs;
  - clock drift between two devices (the drift skip is unit-tested only);
  - acoustic latency;
  - audible quality;
  - the Qt Live audio panel (not compiled).
  "No glitches" is claimed only in this narrow sense: 0 underruns, concealment and dropout blocks in the stated runs (L1 12 s, L3 12 s, L4 about 12 s, L5b/c/d/e about 10 s each), on one PC, loopback or own Wi-Fi address, with test clocks (L4: real devices, silent input).
